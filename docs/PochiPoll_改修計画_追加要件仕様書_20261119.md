# PochiPoll 改修計画・追加要件仕様書

- **文書種別:** 現行仕様書への追加・変更仕様／Codex Cloud向け実装計画
- **版:** 1.0（2026-11-19）
- **対象:** [qsarkbir/PochiPoll](https://github.com/qsarkbir/PochiPoll)（`main`ブランチ。着手時に差分を再確認）
- **既存の基準:** 2026-11-05改訂「FakeSlido仕様書」および現行README・実装・テスト
- **位置づけ:** 現行仕様を全面置換しない。抵触する部分のみ本書を優先し、それ以外は現行仕様を維持する。
- **開発方法:** Codex Cloud。フェーズ・小機能ごとに作業ブランチとPull Request（PR）を分け、レビュー・検証後に次へ進む。
- **Codexサブエージェント:** `review`（reviewer）・`implementer`・`tester`を定義し、高コストモデルは`review`（reviewer）のみに割り当て、他の2者には低コストモデルを使用する。
- **現状確認:** 文書執筆時に確認したリポジトリは `server.js`、`session.js`、`public/*.js`、`test/api.test.js`、`test/load.mjs`、`package.json` から成る。Node.js 24、ブラウザ側は素のHTML/CSS/JavaScript、ビルド不要、ランタイムnpm依存なし。

> **重要:** 本書は**改修計画と受入条件**である。改修コードの作成・テスト実行・Cloudflare経由の実機動作確認を完了したことは意味しない。

## 0. 改修の目的と全体像

### 0.1 目的

1. JavaScriptからTypeScriptへ移行し、開発者がTypeScriptを学べるように型定義・初心者向け日本語コメント・学習用解説を整備する。
2. 講義・会議の運営で起こりやすい保存忘れ、接続不備、セッション失効、操作ミス、送信失敗を防止・軽減する。
3. 選択式の質問に加えて、「お題への匿名コメント投稿＋いいね＋運営者による公開管理」を追加する。

### 0.2 実装順序と完了ゲート

| フェーズ | 範囲 | 完了条件（次フェーズへのゲート） |
| --- | --- | --- |
| **Phase 1** | TypeScript化 | 型チェック、ビルド、既存APIテスト・負荷試験が通り、既存UI・公開手順の後方互換性を確認 |
| **Phase 2** | 最優先・高の運用改善5件 | 5件それぞれの受入テストが通り、実機の運営操作・復帰・消去が確認できる |
| **Phase 3** | コメント＋いいね | 投稿・いいね・承認・公開・非公開・削除・発表・書き出しを一連の操作で確認し、公開範囲の漏れがない |

### 0.3 全フェーズ共通の制約

- **従来の選択式投票を壊さない。** 単一選択／複数選択、4種類のグラフ、回答変更、質問別公開状態、JSON/CSV書き出しを維持する。
- **1プロセス・1セッション、Node.js 24、Quick Tunnelを含むHTTPS公開**を維持。Cloudflareの有料プラン、固定ドメイン、外部DB、外部認証は必須にしない。
- **サーバーに投稿・票・質問の永続保存をしない。** 運営者の明示的なダウンロード以外はメモリに保持し、終了／自動消去で破棄する。
- **匿名参加を維持する。** 参加者の氏名・メールアドレス・アカウント登録は不要。アプリ側で生IP・アクセスログ・個別行動時刻を永続保存しない。
- **管理キーと権限分離を維持する。** 参加者、発表、運営の3権限を混同しない。URLフラグメントとAuthorizationヘッダーによる認証を原則維持。
- **ランタイムの新規依存は原則ゼロ。** TypeScriptと型定義は開発時依存として追加可能。QRコードライブラリは従来の固定・同梱方式を維持。
- **テスト用・開発用の機密情報はコミットしない。** Cloudflareトークン、管理キー、本番コメント、個人情報をテストフィクスチャやPRログに含めない。
- **公開後の表示内容は完全には回収できない。** コメント機能では投稿本文に個人情報等が混入するリスクを明示し、事前審査を既定とする。

### 0.4 対象外

独自ドメイン／Named Tunnel移行、複数主催者、複数イベント同時運用、データベース、外部生成AIによる自動モデレーション、参加者アカウント、画像添付、Markdown/HTML投稿、CSV以外の新たな集計機能、質問複製、グラフ画像書き出し、発表画面の大規模なリデザインは、本計画の対象外とする。必要なら後続フェーズで検討する。

## 1. Phase 1 — TypeScript化（既存機能の維持）

### 1.1 要件

| ID | 要件 | 受入条件 |
| --- | --- | --- |
| TS-01 | アプリ独自のサーバー・ブラウザ用JSをTypeScriptへ移す | 主要ソースは `.ts`。動作時には適切なJSが生成される |
| TS-02 | 型チェックを有効にする | `strict: true` に相当するチェックを有効化し、型エラー0件 |
| TS-03 | 入出力データの型を明示する | `Question`、選択肢形式、状態、集計、API入出力、認証ロールを定義 |
| TS-04 | 入力値の実行時検証は残す | ネットワーク由来JSONを単に型アサーションで信用しない |
| TS-05 | 初心者向けの日本語コメントを付ける | 型・文法の要点と設計理由を説明。無意味な逐行コメントは避ける |
| TS-06 | TypeScript学習用ドキュメントを加える | `docs/typescript-guide.md` に型の基礎、主要ファイル、実例、実行・検証手順を記載 |
| TS-07 | ビルド手順を再現可能にする | `npm ci` → `npm run build` → `npm test` で再現できる |
| TS-08 | 振る舞いを原則変更しない | 既存API・画面・ファイル形式・Cloudflare起動方法・セキュリティ要件が維持される |
| TS-09 | 旧データへの互換性を維持する | `fakeslido-deck` 等の旧JSON形式とブラウザ保存キーを引き続き読み込める |

### 1.2 推奨する移行方式

**TypeScriptコンパイラ（`tsc`）でJavaScriptへ変換する。** Node.js 24の型除去だけに依存せず、ブラウザ用ファイルもビルド対象にする。React、Vite等のフレームワーク・バンドラーは導入しない。

構成例（**実装時にCodexが現在の依存関係を調べて最終決定**）:

```text
src/
  server.ts
  session.ts
  public/
    admin.ts
    participate.ts
    present.ts
    common.ts
    charts.ts
public/                     # HTML/CSS/SVG・同梱QRライブラリなど静的原本
test/                       # 初期段階は既存JSテストを維持可能
scripts/copy-static.mjs     # 静的原本を実行用ディレクトリへ複写
tsconfig.json
package.json
package-lock.json
dist/                       # 生成物。git管理しない
  server.js
  session.js
  public/
    *.js
    *.html
    *.css
    *.svg
    vendor/qrcode.js
```

- ESMの相対importは**生成後の `.js` を指す表記**に統一し、ビルド後にブラウザ・Node.jsが解決できるようにする。
- `src/`と`dist/`を明確に分け、`dist/`を `.gitignore` に追加する。**実行時に使用するHTML/CSS等を `dist/public` へコピーし忘れない**こと。`server.ts` の静的ファイル読み込みパスも実行位置に合わせて検証する。
- `tsconfig` はまず理解しやすい最小構成を目指す。Node/DOMの型環境の分離が必要になれば設定ファイルを分割する。不要なコンパイラ・ビルドツールの重複導入を避ける。
- 依存は原則 `typescript` と `@types/node` を `devDependencies` に追加。ビルド後のアプリにランタイム外部依存を持ち込まない。
- `npm run typecheck`、`npm run build`、`npm test`、`npm run test:load` を用意・更新。テスト実行時に `dist/` の新しい生成物を使うことを保証する。
- 型が不明な外部入力は `unknown` とし、既存の実行時バリデーションで絞り込む。安易な `any`・`as ...`・`// @ts-ignore` の多用は禁止。必要な例外は理由を記す。
- 学習コメントには `【TypeScript】`、設計上の理由には `【設計】` などの区別を使ってよい。重要な概念（型推論、ユニオン型、型の絞り込み、interface/type、Map/Set、Promise、DOM要素のnull、判別可能な型）を実例に結び付けて説明する。
- **移行中にコメント機能などの機能追加はしない。** バグ修正が不可避なら独立コミットとテストを付け、変更理由をPRで説明する。

### 1.3 Phase 1の検証

1. 型チェック・ビルド・ユニットテスト・既存負荷試験が成功する。
2. 複数選択、回答変更、投票クローズ後の禁止、結果公開・非公開、票リセット、JSON/CSV書き出し、全消去／自動消去の既存テストが成功する。
3. `npm start` でローカル起動し、参加者・運営者・発表画面が表示できる。静的アセット・QRコード生成が機能する。
4. `fakeslido-deck.json` 等の**既存ファイルを読み込める**。旧クライアント保存情報も可能な範囲で継続利用できる。
5. **現行JavaScript版とTypeScript版のAPI出力・状態遷移を比較**し、差異がある場合は明記する。
6. コードコメントが初心者に理解できる日本語で、型と実行時の検証の違いを誤解させない。

### 1.4 推奨PR分割

- **P1-1** ビルド環境・ディレクトリ・npmスクリプト・READMEの整備（挙動は維持）。
- **P1-2** 共通型、セッション管理、サーバーAPIのTS化。
- **P1-3** 参加者・運営・発表画面、グラフ、テスト、初心者向け文書をTS化／更新し、統合確認。

各PRは動作する状態を保つ。途中段階で混在が必要なら一時的なJS/TS共存を許容し、最終PRで整理する。

## 2. Phase 2 — 運用時の安心・便利を高める5機能

**対象は、前回優先度「最優先」「高」とした5件に限定する。** すべてTypeScript実装を前提とする。

### 2.1 OP-01 全データ消去前の集計保存確認【最優先】

**目的:** サーバー上の票は復元できないため、保存忘れによる事故を防ぐ。

- 票が1件以上ある状態で「全データ消去」を実行した場合、**消去される質問数・回答のある質問数・総回答件数の参考値**を表示する専用確認ダイアログを開く。
- ダイアログから集計CSV／JSONをダウンロードできる。保存したと思い込ませないよう、**ブラウザが保存の完了を保証するものではない**と明記する。
- 「キャンセル」「（保存済みであることを確認して）消去」を分ける。消去操作は明示的な最終確認後にのみ実行する。
- 票ゼロの場合も従来どおり確認を要する。**保存を必須にはしない**（個人情報を誤投稿した際など、速やかな全消去を妨げない）。
- セッションがダイアログ表示中に変化したら件数を更新し、消去対象のセッションIDの一致をサーバーで検証する。古いセッションに基づく誤操作を防ぐ。
- 既存の管理キー検証・全消去APIを維持。新たなサーバー永続保存は行わない。

**受入例:** 回答あり→警告・ダウンロード可能→キャンセルで票保持／確認消去で全消去・参加コード失効。回答なし→通常の確認。セッション更新済み→旧確認では消去されない。

### 2.2 OP-02 本番前チェック【最優先】

**目的:** 本番開始前に接続・公開URL・画面表示・質問状態の不備を見つける。

- 運営画面に「本番前チェック」を設ける。サーバー到達性、管理認証、参加URL／QRの生成、公開オリジン設定、発表画面の接続状態のうち**自動検証できるもの**を検査する。
- **スマートフォン等の別端末からアクセスできることはサーバー単体では保証できない。** 参加URLを実際に開き、テスト投票して確認する手順を画面上で案内する。
- 質問0件、オープン質問多数、発表対象未選択、通信再接続中などの注意点を表示する。注意と致命的エラーを区別する。
- テスト投票で本番データを混ぜないよう、**本番開始前のテスト質問を作り、確認後に票をリセット／質問を削除する手順**を明示する。初期実装では複数セッション機能を新設しない。
- 実際のCloudflare Tunnel到達性はCodex Cloudの単体テストで「確認済み」としない。**外部端末による手動受入検証**を要する。

**受入例:** 正常なローカル設定→内部チェック成功／QRの別端末確認は未実施と表示。TunnelのURL設定が誤る→該当設定の確認案内。質問未準備→警告を表示。

### 2.3 OP-03 自動消去までの残り時間表示・延長【高】

**目的:** 会議中に予期せずセッションが消える事故を防ぐ。

- 管理者APIは当該セッションの自動消去予定時刻（例 `expiresAt`）を返す。回答者向け・発表画面向けには公開しなくてよい。
- 運営画面に残り時間を表示し、30分前・5分前に警告する（表示は端末上の時計に依存するため、サーバー時刻との差に配慮）。
- 運営者の明示操作による「有効期限を延長」を追加し、既存のアイドル時間ルールで予定時刻を再設定する。延長操作には管理キーが必要。
- **状態取得の自動ポーリングや参加者の投票では延長しない。** プロセス停止やネットワーク切断は延長では救えないことを説明する。
- 警告を開いたまま延長操作が行われた場合、表示を直ちに更新する。

**受入例:** 管理画面表示だけでは期限は伸びない／「延長」で伸びる／期限到来で現行どおりデータとセッション鍵が消去される。

### 2.4 OP-04 次の質問へ進む簡易進行操作【高】

**目的:** 司会者の連続操作を減らす。

- 現行の個別操作（オープン、クローズ、発表対象選択、モード変更）は残す。
- 選択中の質問の「次へ」操作を追加する。既定の振る舞いは**現在の質問をクローズ→次の質問を発表対象に選択→次の質問をオープン→発表を質問モードへ戻す**。
- **前質問の結果公開状態を勝手に変更しない。** 閉じた後も公開済みの結果は閲覧可能。
- 他にオープン中の質問があっても、既定では触れない。複数オープンがある場合はそれが分かる表示・注意を設ける。
- 連続する管理操作の途中失敗を避けるため、サーバー側で**単一の原子的な進行操作**として処理する。連打、2タブ同時操作、最終質問での「次へ」をテストする。
- 未オープン質問は、参加者へ先読み配信しないという既存ルールを守る。

**受入例:** Q1受付中→「次へ」→Q1クローズ、Q2オープン・発表対象、質問モード。Q1の既存結果公開は維持。最後の質問では次へ操作を無効化。

### 2.5 OP-05 投票送信失敗時の再試行【高】

**目的:** 通信瞬断やタイムアウト時に回答が失われるのを防ぐ。

- 受付中の複数選択で、回答変更時にすべての選択を外して保存できる。API は `choices: []` を同じ参加者の回答の取り消しとして受理する。該当の回答がなければ集計値は変わらない。初回の投票は画面上で1つ以上の選択が必要。
- 取り消しは各選択肢の票数、総選択数、回答者数に反映する。参加画面は受理の確認後に回答の控えを削除し、未回答に戻す。
- 回答送信中に通信エラーが生じても、**選択済みの内容を画面に残す**。
- エラーを「通信不通・タイムアウト」「429（混雑）」「409（質問更新／受付終了）」「410（旧セッション）」等に分類して表示する。
- 通信エラー・タイムアウトでは「同じ回答を再送信する」または「回答の取り消しを再送信する」ボタンを表示する。**同一セッション・質問ID・票世代・投票トークン・選択肢**を保持して再送し、二重票にしない。
- APIは同一仮名の回答を置換または取り消す。同じ回答や取り消しを再送しても、集計が二重に変わらないことをテストする。
- 質問が更新／終了した場合は自動再送しない。最新状態の取得と再選択・終了案内へ誘導する。429は`Retry-After`等を考慮する。
- 自動無限再試行は禁止。再送する場合は利用者が再試行できることを明確にする。

**受入例:** リクエストが実際には受理された後に応答だけ失われても、再送で回答者数が増えない。クローズ後の再送は拒否され、回答控えが誤って成功扱いにならない。

### 2.6 Phase 2の推奨PR分割

各機能を原則独立PRとする：`P2-1` 保存確認、`P2-2` 本番前チェック、`P2-3` 残り時間・延長、`P2-4` 次へ、`P2-5` 再試行。全てに対応するAPIテスト・画面テスト・説明更新を添える。

## 3. Phase 3 — コメント＋いいね機能

### 3.1 位置づけと追加の安全原則

新しい質問形式 `discussion`（表示名「コメント＋いいね」）を追加する。既存の`single`／`multiple`は維持し、運営画面から同じ質問一覧の中で混在させられるようにする。**議論用データは投票データと別モデル**にする。コメント投稿は自由記述という新しいリスクを持つため、この形式を選択した質問のみ文字列投稿を許す。

- 既定の公開方式は**事前審査**（投稿は運営者にだけ送信、承認後に一般公開）。質問ごとに「即時公開」を明示的に選べる。
- 文字列はプレーンテキストのみ。HTML・Markdown・添付・画像・外部リンクの自動展開・外部AI審査を初期版では設けない。
- 投稿内容には個人情報や不適切な内容が含まれ得る。**運営者の審査も完全な防御ではなく、一度公開した投稿の閲覧・撮影は取り消せない**。
- 運営者はいつでも投稿受付を停止でき、問題のあるコメントを非公開または削除できる。
- サーバーの質問・票・コメント・いいねはすべてメモリ上のみ。運営者が明示的にJSONをダウンロードしたものは端末側で管理する。

### 3.2 機能要件

| ID | 機能 | 要件 |
| --- | --- | --- |
| CM-01 | お題作成 | 運営者が質問形式 `discussion`、お題本文、審査方式を指定。既存50問上限に含む |
| CM-02 | 投稿受付 | オープン中のお題に匿名でコメントを投稿。受付終了後は新規投稿不可 |
| CM-03 | 投稿共有 | 公開済みコメントのみ、参加者画面と発表画面に共有する |
| CM-04 | いいね | 公開コメントに対して同一ブラウザ／投稿単位で原則1いいね。取り消し可 |
| CM-05 | 並べ替え | 参加者一覧はいいね数降順。同数の場合は投稿順（連番）を維持 |
| CM-06 | 紹介済み | 運営者がコメントを「紹介済み」に設定・解除。公開状態とは独立 |
| CM-07 | 非公開・削除 | 非公開は復元可能。削除は本文・いいね・仮名を消去し復元不可 |
| CM-08 | JSON書き出し | お題、表示順、公開コメント本文、いいね数、紹介済み等を出力。匿名トークンを含めない |
| CM-09 | アニメーション | 発表画面で紹介済み／非公開に切り替わったカードを短時間フェードアウト。動きを減らすOS設定に従う |
| CM-10 | 匿名運用 | アカウント不要。IPによる恒久BANは採用しない。投稿上限・短期レート制限を使う |
| CM-11 | 事前審査 | お題ごとに事前審査／即時公開を切替可。審査待ちの本文は運営者だけが閲覧 |
| CM-12 | 発表表示 | 一覧表示と、運営者が選んだ1件の拡大表示を切替可能 |

### 3.3 お題・コメントの状態遷移

**お題の状態:** 既存質問と同様の `everOpened`・`isOpen` を用いる。`isOpen=false` は投稿受付停止を意味する。既存のグラフ結果公開フラグを、コメント本文の公開判定として**流用しない**。コメントごとの公開状態で管理する。

**コメントの状態（公開権限）**:

- `pending` — 事前審査待ち。参加者・発表画面のAPIに本文を返さない。
- `published` — 公開済み。参加者の一覧・いいね・発表対象になる。
- `hidden` — 非公開。参加者・発表画面のAPIから本文を除外する。管理画面では再公開・削除可能。
- **削除** — 状態フラグを立てるだけにせず、実体の本文・いいね・仮名をメモリから破棄する。削除済み本文は復元・書き出し不可。

**紹介済み状態:** `presented: boolean` を公開状態から独立して管理。紹介済みでも参加者一覧では引き続き閲覧・いいね可能。発表一覧から紹介済みを除外するかどうかは運営側の表示設定で決める。公開可否と紹介の有無は混同しない。

**審査モードの途中変更:** `manual`→`instant`に変えても既存pendingを勝手に一括公開しない。`instant`→`manual`に変えても既に公開済みのコメントを自動非公開にはしない。現在のモードは**新しい投稿にのみ適用**する。

### 3.4 参加者画面

- お題文、投稿フォーム（最大300 Unicodeコードポイントを既定値）、公開済みコメント一覧、いいね数、いいねボタンを表示する。
- 投稿はボタン操作で確定し、受付済み／審査待ち／公開済みの結果を明示する。本文を他人へ公開する可能性と個人情報を入力しない旨を投稿前に注意書きで表示する。
- 投稿上限は**同一ブラウザのトークンにつき1お題3件**を既定とする。運営者がお題単位で1件／3件／制限なしを設定可能。ただし「制限なし」でも短期レート制限と全体上限は適用。
- 公開コメントをいいね数降順で並べる。いいねの取り消しを認める。自分自身の投稿へのいいねは同一トークンでは拒否してよい（初期仕様では禁止する）。
- 通信断中も入力中のコメントを消さない。送信タイムアウト後の再送では`clientSubmissionId`等の冪等キーを使い、同じ投稿が重複しないようにする。
- 参加者は他人の `pending`・`hidden` コメントや他人の仮名を取得できない。自分の承認待ち投稿については、受付結果や受付IDをローカルで確認できればよい（本文をサーバーから一般公開しない）。

### 3.5 運営画面

- お題作成・編集、審査方式、投稿数制限、受付開始・終了、発表対象選択を行える。
- コメント一覧を**承認待ち／公開中／非公開**に切り替えて表示する。各コメントに「承認」「非公開」「再公開」「削除」「紹介済み／解除」「発表で拡大」を設け、状態によって可能な操作だけ表示する。
- 削除には確認操作を要する。削除済み本文は復旧させない。非公開は復元できるため、通常の非表示はまず非公開を使用する。
- 管理画面ではいいね数を確認できるが、匿名参加者の追跡一覧・IP一覧は表示しない。
- 投稿受付の**緊急停止**は一操作で可能にする。コメントを増やさずに閲覧・審査・書き出しを続けられる。
- 既存の「質問集JSON」は再利用可能なお題設定だけを含み、投稿本文・いいねを含まない。投稿結果JSONは別形式にする。

### 3.6 発表画面

- **一覧モード:** 公開中・未紹介のコメントをいいね数順に表示。コメント数が少ない場合も余白を適切に配置し、1～数件でも読みやすくする。
- **注目モード:** 運営者が選択した1件を大きく表示する。非公開・削除になった場合、即座に本文を画面から除外する。
- 紹介済みにすると約200～300msでフェードアウトし、残りを滑らかに移動。`prefers-reduced-motion` が有効ならアニメーションを省略する。
- 投票による頻繁な順位変動で発表画面が動き続けないよう、**発表画面では並び順の更新を抑制／一時固定できる**。参加者画面のいいね順は維持する。
- 発表画面にpending・hiddenコメントの本文や管理者キーを配信しない。スクリーン共有では運営画面を映さない。

### 3.7 データモデル案（仕様上の論理項目。実装時に型を確定）

```ts
// 学習用の概念例。これは完成した実装コードではない。
type ModerationMode = 'manual' | 'instant';
type CommentVisibility = 'pending' | 'published' | 'hidden';

interface DiscussionSettings {
  moderationMode: ModerationMode;
  maxPostsPerToken: 1 | 3 | 'unlimited';
}

interface CommentRecord {
  commentId: string;
  questionId: string;
  body: string;
  sequence: number; // 作成順を示す連番。投票時刻・個人属性は持たない。
  visibility: CommentVisibility;
  presented: boolean;
  // HMAC仮名・いいね集合は管理用の別項目に置き、公衆APIには返さない。
}
```

- 既存 `questionId` をお題にも用い、コメントごとにランダムな `commentId` を付与する。
- 投稿時の匿名識別子は既存の参加者トークンから、お題単位で分離されたHMACを導出する。いいね重複検出はコメント単位のHMACを使う。**生の参加者トークンをサーバーに保存しない**。
- 著者自身のいいね禁止を実現するためには、投稿者識別用の**お題内だけで有効なHMAC**と、いいね操作時の同じトークンから導くHMACを比較する。お題をまたぐ投稿履歴表は作らない。
- いいねの更新は`setLiked: true/false`形式など**冪等**にし、通信再送による意図しない二重加算を避ける。
- 初期上限の目安：**1お題200コメント、1セッション合計1,000コメント、1コメント300文字**。これらは安全側の提案値であり、実測に基づき設定可能にしてよい。上限到達時は利用者に明示する。
- 既存の投票データと混ざらないよう、質問形式に応じた判別可能なTypeScriptのユニオン型で表現する。

### 3.8 API追加・変更案

既存の `/api/public/state` 等は維持し、必要に応じてお題の種類・公開リビジョンを付加する。以下は候補のAPI設計であり、詳細なパス名は実装時に一貫した命名で確定してよい。

| API | 権限 | 主な用途 |
| --- | --- | --- |
| `GET /api/public/comments?questionId=...` | 参加コード | 公開済みコメント・いいね数を取得。変更なしなら204 |
| `POST /api/public/comments` | 参加コード | 投稿トークン、質問ID、本文、冪等キーを送信 |
| `POST /api/public/likes` | 参加コード | コメントIDに対するいいね設定／取り消し |
| `GET /api/admin/comments?questionId=...` | 管理キー | 承認待ち・公開・非公開一覧および投稿数・いいね数 |
| `POST /api/admin/comments/control` | 管理キー | 承認、非公開、再公開、削除、紹介済み、注目表示 |
| `GET /api/admin/export-comments` | 管理キー | コメント結果JSONをダウンロード |
| `GET /api/present/state` | 発表トークン | 公開済みの発表用コメントと表示状態のみ返すよう拡張 |
| `PUT /api/admin/deck` | 管理キー | `discussion`形式・審査設定を含む質問集に対応 |

- 投稿・いいね更新には全てサーバー側で認可、対象セッション一致、受付状態、文字数、形式、リクエストサイズ、レート制限を適用する。
- **承認待ち本文を公開／発表用APIに載せない**。表示を隠すだけでは不十分。
- 多人数利用時の通信量を抑えるため、参加者向けコメント取得は**リビジョンを用いた差分／変更なし応答**などを検討する。2.5秒ポーリングを基本とし、WebSocketの導入は必須にしない。
- 非公開・削除が実行された後は、次の公開状態更新で参加者・発表画面から内容を除外する。通信断・撮影済み画面からの即時回収は保証しない。

### 3.9 投稿結果JSON

- 出力対象：お題ID、質問順、お題文、設定、コメントID、公開コメント本文、いいね数、紹介済み状態、集計スナップショットの書き出し時刻。
- **既定では `published` のコメントだけを出力する。** 必要に応じて、運営者が明示確認して`pending`／`hidden`も含められる拡張余地を残す（初版ではなくてもよい）。
- 削除済み本文、投票・投稿トークン、HMAC仮名、IPアドレス、個人別のいいね履歴は含めない。
- JSONには自由記述本文が含まれるため、**投票の集計CSVよりも慎重な取扱いが必要**であることをダウンロード画面に表示する。
- コメントJSONは再利用用の質問集JSON・既存の集計JSONと形式を区別し、投稿内容のサーバーへの再インポートは初版の対象外にする。

**形式例（ダミーデータ）:**

```json
{
  "format": "pochipoll-comments",
  "version": 1,
  "sessionId": "example-session",
  "exportedAt": "2026-11-19T00:00:00.000Z",
  "topics": [
    {
      "questionId": "topic-1",
      "questionText": "研究データ管理で困っていることは？",
      "moderationMode": "manual",
      "comments": [
        { "commentId": "c1", "text": "DMPの書き方が難しい", "likes": 12, "presented": true }
      ]
    }
  ]
}
```

### 3.10 Phase 3のセキュリティ・負荷・受入テスト

1. **権限:** pending/hidden本文・HMAC仮名・管理操作を参加者・発表画面APIから取得できない。参加コードで運営APIを呼べない。
2. **モデレーション:** manual投稿→pending→承認→公開。即時公開では承認なしで公開。モード切替では既存コメントの公開状態を勝手に変更しない。
3. **表示:** いいね数降順・同数は投稿順。紹介済み切替で発表一覧だけから除外でき、参加者には残る。注目表示に切替可能。
4. **いいね:** 同じトークンからの連打・再送で二重加算されない。取り消し後に再びいいねできる。自分の投稿へのいいねは拒否される。
5. **投稿:** 300文字上限、空白のみ・不正JSON・HTMLとして解釈される文字列・長大リクエスト・大量投稿を適切に拒否／無害表示する。外部URLはクリック可能に変換しない。
6. **消去:** hidden→再公開、削除→本文・いいね消去、セッション全消去／自動消去／プロセス停止→投稿データ復元不可。
7. **書き出し:** 公開投稿・いいね数が対応するお題に紐づき、非公開・承認待ち・削除済み本文や匿名識別子が既定出力に紛れない。
8. **通信:** 送信応答喪失後の再送でコメントが増殖しない。通信断復帰後、公開状態変更や削除が画面に反映される。
9. **発表:** 1～数件でも読みやすく、非公開・削除時に公開表示から除外される。フェードアウトと`prefers-reduced-motion`を確認。
10. **回帰:** 単一選択／複数選択／既存API／CSV・JSON／Cloudflare起動手順を壊さない。本番相当の人数では投票とコメントの混在負荷も検証する。

### 3.11 Phase 3推奨PR分割

- **P3-1** データモデル・検証・投稿／いいねAPI・権限テスト（一般公開はまだ有効化しない）。
- **P3-2** 参加者画面・匿名投稿・いいね・再送・公開済み一覧。
- **P3-3** 運営者画面・事前審査・公開／非公開／削除・受付停止。
- **P3-4** 発表画面の一覧／注目／紹介済みアニメーション、JSON書き出し、統合テスト、README。

**公開解禁ゲート:** すべてのモデレーション・削除・権限テストが通り、運営者の手動確認が終わるまで、コメント形式を一般の参加者向けに有効化しない。

## 4. Codex Cloudでの開発手順

### 4.1 環境と権限

1. Codex Cloudで `qsarkbir/PochiPoll` を接続した開発環境を作成・公開する。開発用VMに **Node.js 24** を用意する。
2. Phase 1着手時は従来の `npm test` と `npm run test:load` を使って**変更前のベースライン**を確認する。フェーズが進んだら `npm ci`・`npm run typecheck`・`npm run build`・`npm test`・`npm run test:load` が使えるよう更新する。
3. `AGENTS.md` を追加し、**本書の参照、改修の段階順序、既存機能の維持、初心者向け日本語コメント、実行する検証コマンド、秘密情報の取扱い**を短く記載する。
4. タスク単位で作業ブランチを使い、**既存の`main`へ直接一括上書きしない**。PRには変更点・テスト結果・手動検証項目・後方互換性への影響を記す。
5. CodexのクラウドVMでは、**ローカルWindows上のTunnelや手元のブラウザの動作確認を実行できたことにはしない**。VM内のループバックテストと、ユーザー端末での手動確認を分ける。
6. 本番の管理キー・Cloudflareトークン・参加者が投稿した本文・ダウンロードしたコメントJSONをCodex環境に渡したり、コミットしたりしない。
7. Codex Cloudのタスクは作業空間が分離される。次のタスクで前タスクの未コミット変更を前提にしない。PRのレビュー・マージ完了をゲートとする。

### 4.2 各タスクでCodexへ依頼する共通ルール

- 対象PRの範囲だけを実装し、後続フェーズへ先回りしない。
- **はじめに現行コードとテストを読む。** 仕様と矛盾する場合は黙って変更せず、PR説明に差異・採用案を記す。
- 既存仕様の不変条件（匿名性・メモリ保持・権限分離・公開APIの制限）を守る。
- 新しい機能と同時に適切な回帰テスト・エラーテストを追加する。
- 動作確認できなかった内容は「未確認」と明記し、テスト成功を推測しない。
- TypeScript学習用の**重要な型と制御フロー**には日本語コメントを付ける。自明な1行の繰り返しは避ける。
- 書き出しJSONの形式と既存データとの互換性を慎重に扱う。変更が必要ならバージョン管理・移行パスを設ける。

## 5. 最終受入条件とリリース判断

**Phase 1の完了判定:** TypeScriptへの移行後に、既存投票機能が同じように使える。型チェック・ビルド・既存テストが成功し、学習用コメントとガイドが揃う。

**Phase 2の完了判定:** 保存忘れ防止、チェック、期限表示・延長、「次へ」、投票再試行が利用でき、特に消去・セッション失効・二重送信に対するテストが成功する。

**Phase 3の完了判定:** コメントを審査して公開し、参加者がいいねし、司会者が紹介済みにし、非公開・削除し、公開範囲に応じたJSONを出力できる。不適切な投稿を運営者が速やかに止められる。

**共通の実機確認:** Windows上の起動、Quick Tunnel越しのスマートフォン参加、QRコード、画面共有、通信断／再接続、複数参加者による投票・いいねを確認する。既存の選択式投票を含めた負荷試験と、コメント投稿混在時の負荷試験を実施する。**Codex Cloudのローカルテストだけで「本番利用に支障なし」とは判定しない。**

## 6. 意図的に残す制約と今後の検討事項

- コメントを投稿可能にしても、匿名参加である限り**厳密な本人単位の重複防止・恒久BANはできない**。IPアドレスの恒久記録・ブロックは採用しない。
- 事前審査を既定としても、運営者の操作ミスや投稿に含まれる個人情報の漏えいはゼロにはならない。一般公開前の運用者向け説明を設ける。
- フェーズ3でコメントが多いと公開APIの通信量・サーバーメモリが増える。ポーリング間隔、差分取得、上限値を実測して調整する。
- データはプロセス再起動で消える。もし本番での可用性が最優先になった場合にのみ、永続保存や代替ホスティングを別件で検討する。
- 独自ドメイン、Named Tunnel、外部モデレーションAI、投稿者による編集・削除、複数イベント同時運用は将来候補に留める。
