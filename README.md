# PochiPoll

会議で使う匿名のリアルタイム投票アプリです。1プロセスで1セッションを運営します。サーバーは質問・票をメモリに保持し、Node.js 24 の標準機能で動きます。

## 起動

Node.js 24 を用意し、GitHub からリポジトリを取得してビルドします。

```sh
git clone https://github.com/qsarkbir/PochiPoll.git
cd PochiPoll
npm ci
npm run build
npm start
```

PowerShell で npm の実行が制限されている場合は、`npm` を `npm.cmd` に置き換えてください。ソースを更新したら、起動前にもう一度 `npm run build` を実行します。

起動時にターミナルに表示される運営用URLを、同じマシンのブラウザで開きます。初期の待受は `127.0.0.1:3000` です。

1. 運営画面で質問を追加し、単一選択／複数選択とグラフを設定します。
2. 運営画面の「発表画面を開く」から別ウィンドウを開き、画面共有します。ローカル起動では「この端末で参加画面を開く」から試せます。スマートフォンなど別端末からの参加には、下記の HTTPS 公開を設定してください。
3. 対象の質問で「受付を開始して発表」を押すと、発表画面がその質問に切り替わります。受付状態を変えずに表示だけ切り替えるには「発表する質問に選択」を押します。
4. 「可視化モード」を押すと結果が公開されます。参加者は回答後に結果を確認でき、受付中は回答を変更できます。「受付を終了」と結果の公開設定は別々に操作できます。
5. 必要に応じて集計 CSV・JSON と再利用用の質問集 JSON を保存します。サーバーを停止するか、「全データ消去」を実行すると、サーバー上の票は復元できません。

通常起動で試すには、同梱のサンプルを保存し、運営画面の「データ管理」→「質問集を読み込む」で選びます。単一選択と複数選択の4問で、4種類のグラフを試せます。[サンプル質問集](public/pochipoll-sample-deck.json)

複数選択の回答を取り消すには、受付中に「回答を変更」を選び、すべてのチェックを外して「変更を保存」を押します。回答者数と各選択肢の票数からその回答が除かれ、未回答に戻ります。受付中はもう一度投票できます。

投票の送信結果を通信エラーなどで確認できなかった場合は、ページを開いている間、参加画面に選択内容が残ります。「同じ回答を再送信する」を押すと同じ票として送られ、受理済みでも重複集計されません。取り消しの送信結果が不明な場合は「回答の取り消しを再送信する」を使えます。混雑時は表示された待ち時間のあとに再送してください。質問が更新された場合は新しい内容を確認して選び直し、セッションが終了した場合は新しい参加 URL を開いてください。

発表対象の質問では「次へ」を押すと、その質問の受付を終了し、一覧の次の質問を開いて質問モードで発表します。公開済みの結果は引き続き閲覧でき、ほかの質問の受付状態も維持されます。続けて進むときは、一覧で発表中の質問をクリックして詳細を表示します。

「全データ消去」の確認画面では、消去する質問数、回答のある質問数、総回答件数を確認できます。回答がある場合は、その場で集計 CSV・JSON をダウンロードできます。必要なファイルが保存先にあることを確認してから消去してください。確認中にセッションが切り替わった場合は、画面を開き直して消去対象を確認します。

運営画面には自動消去までの残り時間が表示され、30分以内と5分以内に警告が出ます。「有効期限を延長」を押すと、その時点から `IDLE_MINUTES` で設定した時間に戻ります。状態取得や参加者の投票では期限は延びません。延長してもプロセスの停止や通信の切断は防げません。

## 本番前チェック

運営画面の「本番前チェック」で、サーバーの応答、運営認証、公開オリジンの設定、参加URL・QR コードの生成、発表画面用 API の応答を確認できます。質問や接続状態の注意点も表示します。

本番前はテスト質問を作成し、発表画面で表示を確認してください。HTTPS 公開時はスマートフォンなどの別端末で QR コードを読み取るか参加URLを開き、テスト投票します。確認後はテスト質問の「設定・管理」から票をリセットするか質問を削除し、本番用の質問を発表対象にします。

## コメント＋いいね（公開前の検証段階）

コメント機能は **通常の `npm start` では無効**です。ローカル試用の `npm run preview:discussion` と結合テストで有効にし、運営者の手動受入が済むまで一般公開を有効化しません。既存の投票の起動・Quick Tunnel 公開手順は変わりません。

手元で確認するには Node.js 24 で `npm ci` → `npm run preview:discussion` を実行します。ビルド後に `127.0.0.1:3001` で試用サーバーが起動し、運営用 URL が表示されます。公開用の `BASE_URL` / `TRANSPORT` 設定は拒否し、通常起動とは別ポートを使います。試用質問集と操作チェック表は [コメント機能の手動受入](docs/discussion-acceptance.md) を参照してください。終了は `Ctrl+C` です。

機能を有効にした検証環境での操作は次のとおりです。

1. 運営画面で回答形式「コメント」を選び、お題・審査方式・投稿上限を設定します。既定は事前審査と1トークンにつき3件です。審査方式の変更は新しい投稿だけに適用されます。
2. 「受付を開始」すると匿名の投稿・いいねを受け付けます。「承認待ち」で本文を確認し、「承認して公開」で参加者と発表画面に表示します。本文には個人情報を入力しないよう案内してください。
3. 「コメント一覧を発表」で公開コメントをいいね順に表示します。「発表で拡大」は1件を大きく表示します。同じボタンは「拡大を解除」に変わり、もう一度押すと一覧へ戻ります。「紹介済みにする」は既定で発表一覧から除きます。紹介済みでも参加者の閲覧・いいねは続きます。「設定・管理」で「紹介済みを一覧から除く」を外すと、発表一覧にも残ります。
4. 順位が頻繁に変わる場合は「設定・管理」の「発表の並び順を固定」を使います。いいね数は更新し、新しく公開した投稿は末尾へ追加します。参加者側のいいね順は変わりません。非公開・削除は固定中や拡大中でも次の更新で除外します。紹介済みの退場は約250msで演出し、端末の「動きを減らす」設定に従います。
5. 通常の非表示には再公開可能な「非公開」を使います。「削除」は確認後に本文・仮名・いいねをメモリから破棄し、復元できません。「受付を緊急停止」は選択中のお題の投稿・いいねを止めますが、閲覧・審査・書き出しは続けられます。
6. 「公開コメント JSON」は **公開済みだけ**を `pochipoll-comments.json` に保存します。紹介済みも含みますが、承認待ち・非公開・削除済み本文や匿名識別子は含みません。自由記述を含むため保存先と共有範囲を確認してください。質問集 JSON・投票集計 JSON とは別形式で、投稿結果の再インポートはできません。全消去の確認画面からも保存できます。

画面共有には発表画面だけを使い、未審査本文や管理情報がある運営画面は映さないでください。発表画面は接続エラーを検出すると表示を取り下げ、復帰後に最新状態を取得します。通信断中や撮影済みの内容を完全に回収することは保証できません。

コメントはサーバーのメモリだけに保持し、停止・全消去・自動消去で失われます。ブラウザの質問集の控えに投稿は保存しません。詳細は [コメント API の開発メモ](docs/discussion-api.md) を参照してください。

## 設定

| 環境変数 | 既定値 | 用途 |
| --- | --- | --- |
| `PORT` | `3000` | ループバックの待受ポート |
| `BASE_URL` | `http://127.0.0.1:<PORT>` | ブラウザから見えるオリジン。パスは不要 |
| `TRANSPORT` | `local` | `cloudflare` または `https-proxy` で HTTPS 公開 |
| `ADMIN_KEY` | 起動時に生成 | 32バイトの乱数を Base64URL で符号化した管理キー |
| `IDLE_MINUTES` | `720` | 管理操作がない場合の自動消去までの時間（分） |
| `VOTES_PER_MINUTE` | `600` | 1分間の送信元ごとの投票リクエスト数 |

管理キーをあらかじめ用意する場合は `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"` で生成し、環境変数 `ADMIN_KEY` として渡します。アクセス時は `<BASE_URL>/admin#<ADMIN_KEY>` を使います。運営用URLは運営者の手元に置きます。

## Cloudflare Quick Tunnel での試用

PochiPoll と `cloudflared` を同じOS環境で実行します。両方を Windows 側で起動するか、両方を WSL 内で起動してください。同じポートでローカル試用中のアプリがあれば、必要な集計を書き出してから停止します。

初回とソース更新時は、上記の手順で `npm ci` と `npm run build` を済ませてください。

1. ターミナル1で `cloudflared tunnel --url http://127.0.0.1:3000` を実行します。表示された `https://…trycloudflare.com` を控え、このターミナルを開いたままにします。
2. ターミナル2で、`package.json` がある PochiPoll のディレクトリから以下を実行します。例示の URL は手順1で発行された URL に置き換えます。

   Windows PowerShell

   ```powershell
   $env:BASE_URL = 'https://example.trycloudflare.com'
   $env:TRANSPORT = 'cloudflare'
   $env:PORT = '3000'
   npm.cmd start
   ```

   macOS・Linux・WSL の Bash

   ```bash
   BASE_URL=https://example.trycloudflare.com TRANSPORT=cloudflare PORT=3000 npm start
   ```

3. ターミナル2に HTTPS の運営用URLが表示されたら、それを開きます。発表画面には HTTPS の参加URLを含むQRコードが表示されます。利用中は両方のターミナルを起動したままにします。

アプリは公開オリジン宛ての `Host` を検証します。Tunnel を同じマシンで動かし、アプリのループバック待受に Tunnel 以外の外部経路を作らない構成で運用してください。この構成で、投票の短時間レート制限に `CF-Connecting-IP` を利用します。

### 接続エラーの確認

- `dial tcp 127.0.0.1:3000` に続いて `connection refused` や `connectex` が出る場合は、アプリ側のターミナルで起動エラーを確認します。Windows では、別の PowerShell で `Test-NetConnection 127.0.0.1 -Port 3000` を実行すると待受を確認できます。`TcpTestSucceeded : True` が目安です。別のポートで起動する場合は `PORT` と Tunnel の `--url` のポートを揃えます。
- 公開 URL が HTTP 421 を返す場合は、起動時に表示された運営用URLのホストと、いま実行中の Tunnel が発行したホストを照合します。Tunnel を起動し直してホストが変わった場合は、必要な集計を書き出し、新しい `BASE_URL` を設定してアプリを起動し直します。

別の HTTPS リバースプロキシを使う場合は、`TRANSPORT=https-proxy` と同じ外部オリジンの `BASE_URL` を設定し、公開オリジンの `Host` を転送してください。このモードのレート制限はアプリから見た接続元単位です。

## 保存されるデータ

- サーバーの票は、質問ごとの HMAC 仮名と選択肢番号の組です。質問と選択肢別の集計値は `pochipoll-results.csv` と `pochipoll-results.json` に書き出せます。
- 参加者のブラウザに回答の控えを24時間保存します。期限切れや旧セッションは次回アクセス時に、票のリセットは次回同期時に反映します。
- 運営者のブラウザに質問集の控えを保存します。サーバーの全消去や再起動後に、運営画面で質問集を復元できます。質問集は `pochipoll-deck.json` として保存されます。旧形式の `fakeslido-deck` も「質問集を読み込む」から再利用できます。復元時の質問は未オープン・結果非公開です。
- 別のブラウザから同じ人が再投票できるため、本人確認が必要な投票には適しません。

## 開発と検証

アプリのソースは `src/` にあり、ブラウザ用のモジュールは `src/public/` にあります。TypeScript コンパイラはこの構成を保って `dist/` に JavaScript を出力します。HTML・CSS・SVG・QR コードライブラリは `public/` から `dist/public/` にコピーします。`npm start` はこの生成物を使います。

アプリの TypeScript は `strict` を有効にして検査します。ES モジュールの相対 import は実行時に解決される拡張子 `.js` を指定します。型と実行時検証の違いや画面から API までの流れは [TypeScript 学習ガイド](docs/typescript-guide.md) を参照してください。

```sh
npm ci
npm run typecheck
npm run build
npm test
npm run test:load
```

`npm test` と `npm run test:load` はそれぞれ最初にビルドし、その生成物を検証します。`dist/` はビルド時に作り直されます。

負荷試験はループバック上で独立したサーバーを起動し、200件の同時投票と結果取得に加え、200参加者の投票・コメント同時送信、いいね、コメント一覧取得、審査後の発表・書き出しへの反映を検証します。Quick Tunnel などの実際の公開経路での性能は、同等の利用条件で別途計測してください。

任意の Chrome 自動操作テストは `test/admin-browser.mjs` と `test/presentation-browser.mjs` です。Playwright はプロジェクトの依存に含めていません。別途用意した Playwright のモジュールディレクトリを `PLAYWRIGHT_MODULE` に指定し、ビルド後に `node test/admin-browser.mjs` / `node test/presentation-browser.mjs` を実行します。一時サーバー・生成した鍵・ダミー本文を使い、参加・審査・発表・非公開・削除・書き出しと通信復帰を確認します。

**公開前の手動確認:** Windows の実運用起動、運営者の目視、Quick Tunnel 越しのスマートフォン参加、QR、発表画面の共有、実際の通信切断／復帰、複数端末での投票・投稿・いいねを確認してください。ローカルの自動テスト成功は、公開経路・利用者端末での受入完了を意味しません。

グラフは HTML と SVG、QRコードは同梱した [qrcode-generator 2.0.4](public/vendor/README.md) で描画します。アプリを動かすための npm 依存はありません。
